# 卅· v4 响应式计算模型（格子）与直接运行

> 本文描述 卅 **v4 的两个根本变化**：
> ① 新的计算模型——**响应式格子**（数据流）；
> ② 前端运行方式的根本改变——**卅.wasm 直接解释执行，彻底告别转译**。

## 1. 为什么另起炉灶

v1–v3 的程序是"顺序执行 + 手动更新"的命令式模型：想改界面，就得写事件处理、
手动刷新显示——这正是 JavaScript 世界的心智负担。v4 把计算模型换成了**数据流**：

> 程序 = 一张会自动更新的依赖图。
> 你声明"什么是什么的函数"，剩下的交给引擎。

这与 Python/JavaScript 的结构差异是**范式级**的：不再写"当输入变化时做××"，
只写"总价是什么"。

## 2. 格子：会自动维护的变量

```saho
单价 = 3.5
数量 = 2

格子 总价 = 单价 * 数量          # 格子：由表达式自动维护
格子 提示 = "单价 {单价} 元 × 数量 {数量} = {总价} 元"

数量 = 5                          # 改依赖 -> 总价、提示自动重算
print(总价)                       # 17.5
```

规则：

| 规则 | 说明 |
|---|---|
| 定义 | `格子 名字 = 表达式`，只能写在程序顶层 |
| 自动重算 | 格子依赖的顶层变量变化后，格子自动重算（不动点迭代，传递闭包全覆盖） |
| 不可赋值 | 给格子直接赋值报错："它由表达式自动计算"——改它依赖的变量 |
| 环禁止 | 格子互相依赖成环会得到明确的双语报错 |
| 读 | 格子就是普通变量：函数里可以直接读它的当前值 |
| 函数内赋值 | 函数内赋值仍是新建局部变量（规范 5.3 不变）——共享状态放字典 |

## 3. 卅.wasm：浏览器里直接解释执行

浏览器只执行 JS/WASM，这是平台事实。卅 的答案是：**把整个解释器编译成
WebAssembly**——服务器和浏览器运行**同一个引擎、同一份代码**：

```
卅.go（同一套 lexer / parser / 求值器 / 标准库 / 响应式引擎）
   ├─ GOOS=windows -> sahou.exe        后端直接运行
   └─ GOOS=js/wasm  -> 卅.wasm      浏览器直接运行（不需要任何转译）
```

- 用户**只写 卅**，永远不会接触生成的 JavaScript（wasm 里没有"生成的源码"）
- `页面` 模块在 wasm 宿主里原生操作 DOM（syscall/js）
- 构建命令：`GOOS=js GOARCH=wasm go build -o 卅.wasm ./cmd/卅wasm`
- 页面只需三个文件：`index.html` + `价格计算.saho` + `卅.wasm`（加一份固定的
  `wasm_exec.js` 加载器），由 `sahou serve` 或任意静态托管提供

## 4. 响应式前端：绑输入与绑定

```saho
单价输入 = 页面.取元素("#单价")
总价显示 = 页面.取元素("#总价")

页面.绑输入(单价输入, "单价")     # 输入框直接驱动变量（数型自动转换）
页面.绑定(总价显示, "总价")       # 变量/格子变化 -> 元素文字自动更新
```

没有事件监听、没有手动刷新、没有 re-render——**改输入，界面自己变**。
完整演示见 `examples/响应式/`（`sahou serve` 后浏览器打开即可体验）。

## 5. 老朋友都在

- 后端 `网络` 模块照常工作（`sahou run`）
- 管道 `->`、花括号块、双语关键字、全角符号——全部照常
- 转译器（`sahou build`）保留作为产出纯 JS 的可选路径，但**不再是前端的标准方式**

## 6. 与设计原则的自检

| 原则 | 自检 |
|---|---|
| 更少的概念 | "格子"一个词讲完整个模型；绑定只有两个函数 |
| 结构显式 | 依赖关系由引擎维护，肉眼可读（`格子 总价 = 单价 * 数量`） |
| 报错即教学 | 环、赋值给格子、非 UTF-8 编码都有双语提示 |
| 不惩罚环境 | 全角符号、分号、UTF-16 文件自动适配 |
| 前后端同语言 | 同一份解释器，同一份 .saho，两种宿主 |
